# AI 智能体小镇 · 单屏Demo

Vue 3 + TypeScript + FastAPI 的六回合开放日游戏。玩家观察、对话和协调4位npc角色 Joe、Wise、Calm、Stead；npc根据状态、记忆、待办与邀请选择下一步活动。新局默认 Mock，可切换真实 AI，后端统一执行和计分。

## 1. 当前页面与入口

| 页面区域 | 当前功能 |
| --- | --- |
| 顶部 | 回合、AI 开关、保存、设置 |
| 概览条 | 模式摘要、四事件完成数、全镇积分、小排行 |
| 概览条条件入口 | 所选居民有对话结果时显示“对话影响” |
| 内嵌控制条 | 开放日贡献榜、支持对象、同起点对照、最近两条贡献；活动建议及反馈 |
| 任务与目标 | 四条专属事件卡，点击选中负责人；长椅发现与修缮入口 |
| 地图和场景 | 小镇全景／居民生活、拖动缩放、地点说明、实际回合移动回放 |
| 底部 | 四名居民属性、最近事件、所选居民聊天、观察／互动／推进回合 |
| 导航和设置 | 角色详情、事件日志、世界状态、图鉴、AI 配置状态、保存／加载／存档列表／重新开始 |

“邀请链路”打开弹窗：可切换四名居民，显示所选居民最近 12 条收发邀请、地点、约定回合、有效期、回应来源与理由、实际结果。无邀请时显示引导。面板只读取后端记录，不通过点击接受邀请或结算得分。


## 2. 玩法与计分

每局 6 回合，每回合 2 次玩家干预。第 0 回合可选择一次支持对象；支持不加属性、不加分。公共目标是至少两类事件产生实际成果；冠军按贡献账本最高分评选，允许并列，无贡献不评冠军。

| 专属事件 | 居民／地点 | 计分条件 |
| --- | --- | --- |
| 邻里交流 | Joe／广场 | 与每位不同居民实际完成事件 +2 |
| 读书分享 | Wise／图书馆 | 准备后广播邀请，每位实际赴约听众 +2 |
| 倾听接纳 | Calm／林间 | 与每位不同居民实际完成倾听事件 +2 |
| 修好长椅 | Stead／林间 | 发现后两次有效修缮，修好 +2；每位实际完成告知互动的居民 +2 |

每位居民专属路线封顶 6 分。同一对象不重复计分；发邀请、接受邀请都不加分。双方选择匹配活动并实际赴约才成立，未赴约或过期不计分。各路线行动成本不同，封顶相同不代表难度完全均衡。

## 3. AI 与 Mock

- Mock：依据精力、性格、待办和邀请的规则优先级选择，不是固定回合脚本。
- AI：自由对话理解玩家语义；回合中四位居民并发调用模型，从服务端合法候选中选择活动并回应邀请。
- 对话可生成角色心情，修改情绪和社交（每项 -8～8），写入记忆、创建或取消待办；聊天不恢复精力。
- AI 失败、超时、非法输出或非法引用会降级。邀请面板按记录显示“AI回应”或“规则回应”；对话来源见“对话影响”。全局开关仅表示启用意愿。
- 模型输出先校验，最终属性、执行、积分和冠军由后端决定。SSE 草稿不是已发生事实。

默认模型配置为 `qwen3.8-flash`，请求显式 `enable_thinking=false`。本版本每次调用时间约为 5 秒。

## 4. 本地启动

以下命令在本 README 所在的 `ai-town-project-demo` 目录执行，不能在外层旧项目目录执行。需要 Python 3.11+、Node.js 24 和 npm。

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
npm --prefix frontend ci
.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

另开一个终端，在同一目录执行：

```powershell
npm --prefix frontend run dev -- --port 5174 --strictPort
```

打开 http://127.0.0.1:5174/ 。Vite 将 `/api` 代理到 8000。健康检查为 http://127.0.0.1:8000/api/health ，它的固定 `mode: rules` 字段不是具体世界的 AI 状态；页面使用世界对象的 `ai` 字段。

旧项目可能占用这些端口。先核对进程及工作目录，避免新版前端连接旧版后端。不要为了启动随意结束其他服务。更换前端端口不会自动更换后端代理地址。

## 5. 配置

将根目录 `.env.example` 复制为 `.env`，只在后端填写：

```dotenv
DASHSCOPE_API_KEY=你的服务端密钥
LLM_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
LLM_MODEL=qwen3.8-flash
LLM_ENABLED=true
```

后端进程设置 `LLM_ENABLED=false` 可强制禁用真实调用。


## 6. 存档与交互协议

前端使用 HTTP JSON 与 POST SSE（fetch + ReadableStream）。写请求携带 `request_id` 和 `expected_revision`；同请求重复返回原结果，不同内容复用 ID 或旧版本提交返回 409。

运行世界位于单进程内存；SQLite 手动保存完整快照，默认 `backend/data/saves.sqlite3`，最多 10 条。服务重启不自动保留未保存进度。旧存档保留原规则，新世界使用 `festival_version=2`。当前没有账号和世界权限隔离。

## 8. 三个体验样例

1. 新局打开“邀请链路”，查看空态并切换四名居民。关闭后选择 Wise，在建议区安排准备分享，推进一回合；再建议发出邀请并推进。重新打开面板，查看三位接收者的待回应记录，此时邀请本身不计分。
2. 继续推进，查看接受／暂缓／拒绝及赴约结果，再对照贡献明细。NPC 不保证接受，没到场不能当作完成。
3. 第 0 回合创建同起点对照，分别打开 Mock 与 AI 世界。向 Wise 输入“想让你到图书馆准备读书分享，准备完成后再邀请大家”。比较回复、待办、实际活动与邀请来源。AI 非确定性，不保证固定冠军；关闭服务端模型后可另行验证降级。

## 9. 技术设计

### 1. 范围与原则

目标是可演示的全栈 Agent MVP：四地点、四居民、六回合开放日，玩家通过对话和建议影响居民，贡献账本呈现实际结果。

前端只负责输入、展示和动画；FastAPI 是世界状态的权威来源。LLM 理解语义并选择候选，不能直接改世界、积分或冠军。规则与 AI 使用同一执行器。

### 2. 当前页面信息架构

- 顶部：回合、AI 开关、保存、设置。
- 概览条：模式、事件完成数、总分、排行摘要，常驻“邀请链路”入口；对话影响／长期意图按选中居民的数据出现。
- 内嵌控制条：紧凑 FestivalPanel 与 SuggestionPanel，包含支持、对照世界链接、贡献摘要和建议操作。
- 中部：导航、EventTasks 四任务、BenchEvent、两种地图视角、场景信息。
- 底部：四居民属性、最近事件、自由对话、玩家操作和回合推进。
- 弹窗：邀请链路、对话影响、长期意图、结局、角色信息、完整日志、近期记忆、设置与存档等。


### 3. Agent 全流程

```text
玩家文本 → 对话理解 → schema/业务校验 → 属性与记忆/待办
                                             ↓
世界快照 → Perception → Mock 或 LLM Decision → Validation
                                             ↓
                     邀请回应与双方配对 → Simulation
                                             ↓
                     Festival 账本 → Memory → 下一回合
                                             ↓
                                API/SSE → 页面与动画
```

`perception.py` 只提供必要状态、公共安排及有限真实记忆；未完成承诺的来源优先保留，当前最多选取 6 条记忆。`agent_decisions.py` 并发请求四位居民的选择，校验候选 ID、记忆引用和邀请回复。单人调用失败只使该人降级，不伪造 AI 成功。

角色心情是模型生成的角色表达，不是模型内部思维过程。当前记忆以结构化记录和有限检索为主，没有向量数据库或通用外部工具调用。NPC 的自主性是合法活动集合内的策略选择。

### 4. 自由对话

`dialogue.py` 区分 request、cancel、emotion、chat。返回自然语言回复、角色心情、是否接受、活动／地点或取消目标、情绪／社交变化、记忆引用。

Pydantic 限制变化为 -8～8；执行层检查地点、角色资格、待办容量和取消目标。聊天不恢复精力，任务在后续回合执行。拒绝不新增承诺，非法安排不生效。降级复用规则消息处理，并保留来源与原因。

限制：schema 和白名单能限制执行权限，但不能证明每一句角色文案都完全合理，也不能保证引用了记忆就充分利用了该记忆。需要语义对照样例验证。

### 5. 四事件与邀请状态机

| 事件 | 前置与执行 | 积分 |
| --- | --- | --- |
| Joe 邻里交流 | 邀请对象，双方在广场完成互动 | 不同对象各 +2 |
| Wise 读书分享 | 准备 → 广播 → 主持与听众匹配 | 不同听众各 +2 |
| Calm 倾听接纳 | 邀请表达者，双方在林间完成互动 | 不同对象各 +2 |
| Stead 修好长椅 | 发现 → 两次修缮 → 邀请居民进行告知互动 | 修好 +2，不同告知对象各 +2 |

邀请字段：id、group、event、sender、recipient、place、due_turn、expires_turn、status、response_reason、response_source、result。广播用 group 关联多位接收者；每人有独立回应和结果。

状态包括 pending、accepted、deferred、declined、completed、expired、cancelled。暂缓或接受可继续改变安排；不能把它画成必然走向成功的直线。

`invitations.resolve()` 在同一回合匹配双方合法活动、邀请及地点；匹配失败不计分，未过期机会可保留。`finish()` 记录执行结果并发出新邀请。过期和撤回有相应处理。面板展示当前状态与最近回应，不是完整的逐次状态变更时间线。

`festival.py` 只根据实际完成结果写账本，用事件／对象唯一键去重，每位居民封顶 6 分。最高分可并列，零分不评冠军；玩家支持不参与算分。至少两类贡献达成开放日公共目标。

限制：通用 run_event/join_event 的互动效果仍主要是确定性规则，尚未实现针对每个困扰的丰富 NPC 交流生成；四路线行动成本不同，需要模拟评估平衡。

### 8. 一致性、存储与模型边界

- `request_id` 与请求指纹防止重复结算；同 ID 不同请求返回 409。
- `expected_revision` 防止过期客户端覆盖新世界。
- 全局 RLock 内 deepcopy → operation → enrich → revision 增加 → 替换正式世界，中途业务异常不提交副本。
- 模型请求在回合快照上并发，全部返回后统一执行，不让迟到模型直接写状态。
- SQLite 保存手动 JSON 快照，最多 10 条；运行世界在内存，不能直接用多个 worker 横向扩容。
- 新局 festival_version=2；旧档保留旧规则，不静默重算历史积分。旧局没有新版四任务数据时，当前新版任务区可能为空。
- 服务端读取 Key，非思考模式、流式输出，单次输出上限 800 token；HTTP timeout=12 秒，并有流式时间预算，不承诺固定响应时间。
- 玩家输入和记忆视为数据；AI 结果必须通过 schema、候选和引用校验。失败记录来源并回退规则。

当前全局锁包含模型等待，多个世界会排队；没有账号、限流、运行世界持久化和完整监控。公网使用前应明确受控体验范围。SSE 减少体感等待，不降低模型完成计算所需时间。

### 9. 本人的关键决策

#### 9.1 前端风格与双地图视角

**问题与选择**：小镇既需要叙事氛围，也需要让玩家看懂居民活动。界面风格参考《巫师 3》的奇幻叙事气质，采用深色面板、羊皮纸质感和金色强调色，并分别设计小镇全景鸟瞰图与居民生活的平面 2D 视角。

**设计理由**：全景用于认识地点及空间关系，居民生活视角用于观察位置、移动与活动结果。

**取舍与验证**：双视角增加位置映射和动画维护成本；全景优先氛围，2D 优先行为可读性。

#### 9.2 四位 NPC 的角色设计

**问题与选择**：选择用人格、初始属性、活动偏好和专属事件共同定义四位居民。

| NPC | 人格与角色定位 | 专属事件 | 需要呈现的行为特点 |
| --- | --- | --- | --- |
| Joe | 外向乐观，主动接触邻居 | 邻里交流 | 主动寻找交流机会，同时受精力和已有安排约束 |
| Wise | 内敛思考，重视知识表达 | 读书分享 | 从准备走向邀请与分享，需要协调实际听众 |
| Calm | 温柔，善于倾听 | 倾听接纳 | 接纳他人的表达，也需要照顾自己的状态 |
| Stead | 务实，重视行动成果 | 修好长椅 | 完成修缮，并通过告知让其他居民了解成果 |

**设计理由**：人格影响表达与偏好，属性限制当前行动，记忆和承诺影响后续安排，专属事件提供可观察的贡献路径。希望角色差异不仅体现在台词，也体现在接受请求、处理邀请和选择活动的方式上。

**取舍与验证**：专属职责由后端规则限定，LLM 决定何时推进、怎样回应及是否赴约，不自行发明职业或职责。可向不同居民输入相同请求，对照回复、待办及下一回合选择。

#### 9.3 四条专属事件与回合制玩法

**问题与选择**：开放式小镇容易缺少明确目标，玩家也不容易判断自己的干预是否有效。我采用四条角色专属事件和六回合开放日，让共同建设与最佳居民评选形成一次有起点、过程和结果的体验。

**玩法节奏**：观察状态 → 对话或提出建议 → 推进回合 → NPC 选择活动 → 后端执行 → 查看贡献和记忆变化。玩家负责协调、支持居民，但不能直接指定冠军；公共目标至少完成两类贡献，个人排名由真实贡献账本决定。

**设计理由**：事件让玩家知道能推进什么，回合边界把观察、决策、执行分开，便于理解因果、验证结果及录制讲解。六回合限制演示范围，而不是持续增加地图、居民和复杂经营系统。

**取舍与验证**：角色专属事件减少自由职业式玩法，回合制也没有实时世界持续运转的感觉。各路线同样封顶 6 分，但行动成本不同，不代表难度已经完全均衡。后续应通过多局模拟统计路线完成率、缺席比例、贡献与冠军分布，再决定是否调整成本或邀请有效期，不给 AI 模式额外积分。

#### 9.4 AI／Mock 共用规则，执行权交给后端

**问题与选择**：生成模型可能输出不存在的活动、虚构完成结果或不合理分数。我让模型负责理解语义和选择合法候选，由后端验证活动、地点、邀请、记忆引用及状态，统一执行并结算。AI 与 Mock 共用这套执行规则。

**设计理由**：在相同初始快照和世界规则下比较两种策略，差异来自理解与选择，而不是特权加分。即使模型说“分享成功”，也必须核对准备、邀请以及主持和听众的实际匹配，才能产生贡献。

**失败处理**：单个 NPC 的 AI 调用失败时回退规则策略，保留来源与失败原因，再进入同一个执行器。模型输出没有直接修改世界和冠军的权限；请求幂等与版本检查继续保护最终提交。

**取舍与验证**：有限候选约束了开放式创造能力，但能提高可解释性和可靠性。通过同起点对照、非法输出测试与降级测试验证边界。AI 的价值可以体现在理解隐含请求、利用记忆和差异化回应，不保证每局得分更高或获得固定冠军。

#### 9.5 SSE 事件流与只读邀请弹窗

**等待体验的选择**：一次操作包含模型生成、校验和执行，完全等待最终响应会让页面显得无反馈。因此使用 HTTP POST SSE 持续展示进度与草稿，正式世界仅以最终结果更新。SSE 减少无反馈等待，不保证模型计算更快，也不承诺总耗时始终低于 5 秒。

**协作展示的选择**：主屏保留地图、任务和操作，将邀请详情放入只读弹窗。玩家可以核对谁邀请了谁、约定回合、回应来源和实际结果，但不能通过浏览面板替 NPC 接受邀请或增加贡献。

**取舍与验证**：弹窗需要一次额外点击，但避免继续挤压单屏。接受不等于赴约，赴约与得分由后端核验；当前面板展示当前状态和最近回应，不是完整的状态变更时间线。SSE 测试验证分片和最终结果处理，邀请页面测试验证来源、状态、切换与关闭重开，并确认浏览前后世界 revision 不变。
